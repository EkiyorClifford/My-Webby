02 — Database Design

users (id, name, email, role) properties (id, landlord_id, title, location, price) inspections (id, user_id, property_id, status) approvals (id, inspection_id, status)

Designed to separate user actions (inspections) from decisions (approvals), allowing flexible workflows and future automation.

03 — Backend Logic

POST /register POST /login
GET /properties
POST /inspection/request
Request body:
{ "user_id": 12, "property_id": 45, "date": "2026-04-20" }
POST /inspection/approve POST /inspection/reject

Backend handles state transitions between user actions and landlord decisions, ensuring consistent data flow across the system.

04 — Design Decisions

Instead of allowing direct booking, an inspection layer was introduced to control access, validate intent, and reduce landlord risk. This structure also creates a natural checkpoint for future features like payments, scheduling, and automated approvals.

05 — State Handling

inspection.status: - pending - approved - rejected

State-based design ensures predictable transitions and prevents conflicting actions between users and landlords.

06 — System Insight

The core challenge was balancing user freedom with landlord control. By introducing structured workflows instead of direct interactions, the system ensures trust, reduces friction, and keeps both sides aligned without relying on intermediaries.
