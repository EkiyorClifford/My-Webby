01 — System Flow

1 User registers account
→
2 Browses available properties
→
3 Requests inspection
→
4 Landlord reviews request
→
5 Approval → booking confirmed

02 — Database Design

users (id, name, email, role) properties (id, landlord_id, title, location, price) inspections (id, user_id, property_id, status) approvals (id, inspection_id, status)

Designed to separate user actions (inspections) from decisions (approvals), allowing flexible workflows and future automation.

03 — Backend Logic

POST /register POST /login GET /properties POST /inspection/request Request body: { "user_id": 12, "property_id": 45, "date": "2026-04-20" } POST /inspection/approve POST /inspection/reject

Backend handles state transitions between user actions and landlord decisions, ensuring consistent data flow across the system.

04 — Design Decisions

The system is structured to avoid tight coupling between users and properties. Instead of direct booking, an inspection layer introduces control, validation, and future monetization opportunities.

05 — State Handling

inspection.status: - pending - approved - rejected

State-based design ensures predictable transitions and prevents conflicting actions between users and landlords.
